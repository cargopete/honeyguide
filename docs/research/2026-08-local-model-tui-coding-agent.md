# Building a Local-Model TUI Coding Agent for Qwen3-MoE Class Models

> Archived research, August 2026. This is the input document that RFC-0001 is built on.
> It is preserved verbatim as the record of what was believed before anything was measured.
> Where later measurement contradicts it, see `docs/measurements/` and RFC-0001 §5.

## TL;DR
- **Build it, but abandon the architecture ward used.** Ward failed for structural reasons — a naive `<<<SHELL:…>>>`/`<<<SAVE:…>>>` marker protocol, no diff/edit format, no repo index, whole-file writes, and single-shot execution with no validation loop. Those are exactly the failure modes that break 3B-active-param models. The right design is: Rust/ratatui TUI, a **strong-model-built offline index** (rust-analyzer SCIP + tree-sitter repo map + per-module summaries + AGENTS.md), a **narrow 3–5 tool surface**, **search/replace edit blocks** (not unified diffs), **grammar-constrained tool emission**, one-tool-per-turn ReAct, and a **deterministic `cargo check` gate** before any edit is accepted.
- **The "asymmetric intelligence" idea is sound and is the single highest-leverage decision.** Published evidence (arXiv:2605.26720) shows strong-model plans injected into a weak model's context "consistently improve execution success," and the effect is largest within the same model family — the paper's own example is Qwen3-235B-A22B → Qwen3-Coder-30B. For your small Rust projects, precompute the index once with Claude, refresh it incrementally, and keep the local model's job to "consume the map + make a small edit," never "explore the repo."
- **Qwen3-30B/35B-A3B is a viable local driver, but only inside a tight harness.** It has documented, reproducible tool-calling breakage (Hermes-vs-XML template mismatches, empty tool calls, XML leaking into content once >~5 tools are exposed). On your Ryzen 9 5950X (CPU-only, DDR4) expect roughly single-digit-to-low-teens tokens/sec generation; on an Apple Silicon Pro expect ~40–60 tok/s. That budget forces small context and few round-trips — which is exactly what the index-first design delivers.

## Key Findings

**1. Ward's design is a textbook small-model anti-pattern.** The repo is ~120 lines of Sage + ~280 lines of Rust FFI, explicitly a "reference application for the Sage programming language," not a serious agent. Its entire tool protocol is: the LLM emits `<<<SHELL:command>>>` and `<<<SAVE:filename>>>…<<<END>>>` markers, which are regex-parsed. There is no diff/patch format (files are fully written), no repo index/map, no schema or grammar constraint on outputs, no retry-on-malformed, no compile/validation gate, and a single agent under a `OneForOne` supervisor with no ReAct loop. Every one of these is a known small-model failure amplifier.

**2. Every general-purpose agent harness that leans on native function-calling degrades badly with local Qwen-class models.** OpenCode, Crush, Goose, and Cline all have long issue threads describing the same cluster: the model "thinks about" which tool to use but never emits a call; tool JSON is printed to chat instead of executed; XML tool tags leak into the content field; the loop terminates on an empty tool call. Two root causes dominate: (a) **context truncation** — Ollama silently defaults to a 4096-token window, truncating the system prompt and tool defs (`truncating input prompt limit=4096`), which looks like "the model can't use tools"; and (b) **template/parser mismatch** — e.g., Ollama wiring the Hermes JSON renderer to a model trained on the Qwen3-Coder XML tool format (Ollama issue #14493).

**3. Edit format matters more than raw coding skill for small models.** Aider's own guidance: weaker/lesser-known models default to the "whole" format because it is easiest, and "most local LLMs struggle even with the whole format." The Diff-XYZ benchmark (arXiv:2510.12487) found **search/replace is the best format for stronger models** (GPT-4.1 hits 0.96 exact-match on Apply with search/replace, beating all unified-diff variants) and warns that "small models may confuse single-character udiff markers (+, -, leading space) with ordinary code characters." Critically, Diff-XYZ also found that *small open models "benefit little from any formatting choice"* — so for a 3B-active model the right move is to pick the format that is **easiest to validate deterministically**, which is **search/replace matched against the on-disk file**, not to expect any format to rescue accuracy.

**4. Qwen2.5-Coder-32B scores only ~8% on Aider's polyglot benchmark** ("currently Qwen2.5-Coder-32B-Instruct is only 8% completed correctly," per QwenLM Discussion #1139) despite strong single-shot HumanEval/BigCode numbers — a direct illustration that agentic edit-format competence ≠ code-generation skill. Frontier models on the same benchmark sit at 45–88% (Claude-3.5-Sonnet 45.3%, o1 61.7%, GPT-5 0.880). Aider defaults unknown models to whole format for exactly this reason.

**5. Code-as-action and constrained decoding are the two techniques with the best evidence for lifting weak-model reliability.** CodeAct (executable code as the unified action space; Wang et al., ICML 2024, arXiv:2402.01030) achieves "up to a 20% absolute improvement over baselines while requiring up to 30% fewer actions"; on M³ToolEval, gpt-4-1106-preview showed "a 20.7% absolute improvement compared to the next best action format (text) while requiring 2.1 fewer interaction turns on average." Separately, grammar-constrained decoding (llama.cpp GBNF, Ollama `format`/JSON-schema via XGrammar, Outlines, LLGuidance) makes syntactically-invalid tool calls *mechanically impossible*. The trade-off is real: Tam et al. 2024 ("Let Me Speak Freely?", EMNLP) found strict format constraints cause **10–30% reasoning performance degradation** because "the model may be forced to output answer fields before completing chain-of-thought reasoning," and the tax is proportionally worse for sub-3B-active models. The mitigation is well established and later work characterizes the tax as "mostly a prompt artifact, not a decoder artifact": **let the model reason freely first, then switch to constrained generation for the tool-call block.**

**6. Abliteration degrades exactly the capability you depend on — structured/tool output.** Community testing reports abliterated Qwen variants (notably the huihui-ai line) are "weaker on tool calls and MCP integrations compared to the base models," and that for tasks needing "structured output or tool use, a fine-tuned uncensored model may outperform an abliterated one." Heretic's methodology (p-e-w's KL-divergence-minimizing parameter search) is explicitly designed to limit this damage — "retains as much of the original model's intelligence as possible" — and benchmarks favorably on MMLU/GSM8K. But those benchmarks don't test tool-calling, so there is **no direct measurement that heretic-Qwen retains tool-call reliability.** Practical implication: do not rely on heretic's native function-calling; drive it with grammar-constrained emission and validate every call.

**7. Hardware budget forces the index-first design.** On your Ryzen 9 5950X CPU-only with DDR4, MoE generation is memory-bandwidth-bound; expect roughly **~8–15 tok/s generation** (community reports ~12–15 tok/s on faster DDR5 CPUs; DDR4 dual-channel ~50GB/s lands at the low end), with prompt processing much faster on 16 physical cores (~16 threads optimal; SMT hurts). There is a documented llama.cpp issue (#19480) where MoE CPU inference "isn't taking advantage of the sparse activation pattern — it appears to be reading far more data than the 3B active params require," making it slower than bandwidth math predicts (worst for Qwen3-Next; classic 30B-A3B less affected; the `ik_llama.cpp` fork handles it better). On Apple Silicon Pro, MLX 4-bit delivers **~40–60 tok/s** (M4 Max hits 68–100 tok/s; MLX consistently beats GGUF/Ollama, ~68 vs ~40 tok/s on the same M4 Max). At these speeds, every avoided round-trip and unsent token is real wall-clock time — the index is what keeps sessions usable.

## Details

### Why ward "kinda failed" — diagnosis
Ward is a language demo, and its choices are the canonical ways small-model agents break:
- **Marker-based tool protocol with no constraint.** `<<<SHELL:…>>>` / `<<<SAVE:…>>>` is parsed by string matching. A 3B-active model will (a) forget the exact marker syntax, (b) wrap it in prose or markdown fences, (c) emit it inside a reasoning/`<think>` block, or (d) hallucinate a close tag. Nothing forces the format, so drift at temperature > 0 is guaranteed.
- **Whole-file writes.** `<<<SAVE:filename>>>…` rewrites entire files. For anything but trivial files this triggers "lazy coding" (eliding sections with `// ... rest unchanged`), silently drops code, and burns your scarce token budget.
- **No index / no map.** The model must explore via shell (`ls`, `cat`) every session, spending tokens and turns on navigation — the single most expensive thing to ask a slow local model to do.
- **No validation gate.** Edits are written to disk unconditionally; there's no `cargo check` before accept, so a broken edit is indistinguishable from a good one until the human notices.
- **Single-shot, no ReAct loop, no retry-on-malformed.** One parse; if it fails, the turn is wasted.

### THREAD 1 — Landscape, honestly assessed

**Rust-native references worth studying/forking:**
- **openai/codex (`codex-rs`)** — the best architectural template you have. It's Rust, TUI via **ratatui** (`codex-tui`, immediate-mode redraw, insta snapshot tests), with a reusable **`codex-core`** crate that owns the agent loop, thread lifecycle (create/resume/fork/archive), context compaction, and sandboxed tool dispatch. Its **Submission-Queue/Event-Queue** split decouples the TUI from the agent engine — copy this pattern; it makes alternative frontends and headless runs trivial. Caveat: Codex is tuned for OpenAI frontier models over the Responses API and, per third-party analysis, "bets against local LLMs." You're borrowing structure, not model assumptions.
- **Aider** — not Rust, but the reference implementation for the two ideas you most need: the **tree-sitter repo map** (PageRank over a symbol-reference graph, budgeted to ~1k tokens by default via `--map-tokens`, SQLite-cached to avoid re-parsing) and **edit-format engineering** (whole / diff / udiff / editblock / patch). Steal the repo-map algorithm and the search/replace ("editblock") coder wholesale. Standalone reimplementations exist (RepoMapper/RepoMapper MCP) as reading references. Note Aider's own caveat: "weaker models get easily overwhelmed and confused by the content of the repo map" — so budget it tightly and rank hard.
- **Other Rust scaffolding to borrow from**: `pi_agent_rust` (single-binary, bounded-resource sessions, capability-gated tool execution, dangerous-shell-intent blocking), `adk-rust` (typed Rust tools, Codex/Hermes-style loop modes, `cargo check`-style verify loops), and the **Agent Client Protocol Rust SDK** if you ever want editor interop. Libraries, not products.

**General agents and how they fare with local Qwen-class models:**
- **OpenCode** (TypeScript) — good local story on paper (OpenAI-compatible Ollama provider; docs require 64k+ context). Real reports: models "generate text describing edits or summaries instead of emitting actual tool calls," and "smaller and reasoning-distill models showed exactly this." Community winners are Qwen3-Coder-class MoEs *with `num_ctx` raised to 16k–64k* (the 4k default silently breaks agentic use).
- **Crush** (charmbracelet, Go) — polished TUI, but local support has been a persistent pain point: config duplication, persisted "thinking" options sent to models that don't support them (causing API errors after switching to Ollama), and the same Ollama-context-truncation trap (`truncating input prompt limit=4096`). Native Ollama auto-discovery (`type: ollama`, omit models list) landed but is still rough.
- **Goose** (block, Rust) — most instructive for you because it confronted the problem head-on with a **"toolshim"**: a small local model translates the primary model's prose into tool calls, guided by Ollama structured outputs (`GOOSE_TOOLSHIM=true`). Their own finding: shim performance is limited by the small model's instruction-following, is "quite sensitive to prompting," and "structured output interference" perturbs sampling. They also document that **Qwen3-Coder emits native JSON tool calls only with ≤~5 tools; beyond that (Goose's developer extension exposes 11) it switches to XML tool tags inside the content field and the loop breaks** (issue #6883). This is a direct, hard argument for a tiny tool surface. Goose's benchmark also shows Qwen2.5-Coder-32B at 0.80 on their vibe-check when tool-calling works.
- **Cline** — the most demanding harness (long, growing context; repeated structured tool calls). AMD's testing: models smaller than Qwen3-Coder-30B "consistently fail," **Q4_K_M is the practical quant floor** (Q3/Q2 degrade tool-calling before chat quality), and even 30B often needs "Compact Prompts" enabled. Per ModelFit's tier list, **Qwen3-Coder-30B is the consensus local default at ~96% well-formed tool calls** (Llama 3.3 70B highest at ~97%); the whole point is "reliable structured tool-calling under a long, growing context window… matters far more than raw benchmark coding skill."
- **Plandex, OpenHands, RA.Aid, gptme, Continue, Tabby, smolagents, Qwen Code/Gemini CLI** — all usable, none solve the small-model reliability problem in a way you'd want to inherit. Qwen Code (fork of Gemini CLI) is the most Qwen-tuned but is a full CLI, not a minimal harness.

**Bottom line on Thread 1:** No existing tool is tuned for "3B-active model + pre-built index + tiny tool surface + Rust." Fork the *architecture* from `codex-rs`, the *repo map and edit format* from Aider, and the *toolshim/tiny-surface lessons* from Goose. Don't adopt any of them as-is.

### THREAD 2 — Making a 3B-active model reliable

**Tool-call format — ranked for Qwen3-MoE:**
1. **Grammar-constrained emission of a minimal structured call, with a free-text reasoning prefix allowed.** Use llama.cpp GBNF (or Ollama `format` JSON-schema, which uses XGrammar) to force the tool block to be valid. Keep schemas flat (avoid 4+ nesting levels; put any `reasoning` field *before* the answer field; describe every field in the prompt prose because Ollama silently ignores schema `description`).
2. **Code-as-action** for multi-step operations, if you're willing to run a sandboxed executor — highest success/turn efficiency (CodeAct: +20% success, −30% turns), but heavier to build and riskier to sandbox. For "small targeted edits," a fixed tool set is simpler than a code interpreter; keep this in reserve.
3. **XML-style tool tags** (Qwen3-Coder's native training format) — acceptable, but parse tolerantly: Goose's bug was that any non-tool text alongside the tag caused the whole message to be treated as text. If you go this route, use `--jinja` with the correct chat template and a lenient XML extractor.
4. **Native JSON function-calling via Ollama** — *do not depend on this.* Documented broken across the Qwen3.x line (wrong renderer wired, empty tool calls terminating the loop, unclosed `<think>` blocks corrupting subsequent turns). If used at all, keep to ≤5 tools.

**Harness design rules (each maps to a documented failure):**
- **Narrow tool surface: 3–5 tools max.** `read_file(path, range?)`, `search(query)`, `apply_edit(path, search, replace)`, `run_check()` (runs `cargo check`/`cargo test`), optionally `finish(summary)`. Directly avoids the ">5 tools → XML leakage" cliff.
- **One tool per turn, forced ReAct loop.** Reason → single tool → observe → repeat. Never let the model batch actions.
- **Grammar-constrain the action; allow a short reasoning prefix.** Two-phase (reason unconstrained, then constrained tool block) to dodge the 10–30% reasoning tax.
- **Retry-with-repair on malformed output**, capped (Aider caps reflections at 3; do the same). Feed the parser/compiler error back verbatim.
- **Deterministic guardrail: never accept an edit that doesn't compile.** Apply edit to a scratch copy → `cargo check` → accept or bounce with the compiler error. This is your single biggest quality multiplier and spends zero model tokens.
- **Search/replace edit blocks, matched against on-disk text**, with unique-match verification; reject and re-prompt if the search block isn't uniquely found.
- **Keep context tiny by leaning on the index** rather than letting the model `cat` files. Send the relevant module summary + symbol signatures + only the specific function bodies the task touches.

**Context budget on your hardware:** Qwen3-30B/35B-A3B supports 256k natively (extendable to 1M via YaRN), but at ~8–15 tok/s CPU-only you cannot afford to fill it. Target a **working context of ~16k–32k tokens**: small system prompt + tool defs, the pre-built index slice for the task, the 1–3 files in play, and a compacted history. Raise Ollama's `num_ctx` explicitly (the 4096 default is the #1 cause of "tools don't work"; set `OLLAMA_CONTEXT_LENGTH` or bake a model variant). Use context compaction (summarize old turns) once history grows — `codex-core` does exactly this.

### The asymmetric-intelligence index — what Claude builds offline
This is the core of your tool, and the evidence supports it directly. Strong-model plan injection into a weak model "consistently improves execution success," with gains "larger when strong and weak models belong to the same model family (e.g., … Qwen3-235B-A22B → Qwen3-Coder-30B)" (arXiv:2605.26720). In plan-then-execute framing, the planner does architecture/reconnaissance and the executor "does not need to reason about architecture — the planner already did that; it translates a precise specification into correct, convention-following code." Translate that from a per-task plan into a *persistent, refreshable index*:

**Index contents for a Rust project (generated by Claude, stored in-repo, e.g. `.agent-index/`):**
- **`AGENTS.md` project brief** — stack, build/test/lint commands (the "definition of done"), architectural rules, naming conventions, "never touch" files, crate layout. This is the CLAUDE.md/AGENTS.md convention (OpenCode seeds it via `/init`); it's the difference between "an agent that works for your codebase" and one that "works for Stack Overflow's idea of your codebase."
- **Structural symbol index from `rust-analyzer scip`** — rust-analyzer has a first-class CLI (`rust-analyzer scip <path> [--output …]`) that emits a compiler-grade SCIP index: every symbol, its kind, type signature, definition location, and cross-file references/monikers. This is *far* more precise for Rust than tree-sitter alone (type-aware, resolves generics/traits). Query it to answer "who calls `validate_user`?" in ~1ms instead of file reads. (LSIF output is also available if you prefer.)
- **Tree-sitter repo map (Aider-style)** — PageRank-ranked symbol map budgeted to a fixed token count, as the fast "overview" the model sees first. Complements SCIP (breadth vs. precision). Keep it small — big maps confuse small models.
- **Per-module and per-file summaries** — 2–5 sentence natural-language summaries Claude writes for each module: responsibility, key types, invariants, gotchas. These let the weak model "understand" a file without reading it.
- **Call graph / dependency edges** — from SCIP references; lets the harness compute the "blast radius" of an edit and pull exactly the right context.
- **Type-signature catalog** — public function/method signatures and key struct/enum/trait defs, so the model writes code that fits existing abstractions.

**Refresh strategy:** generate fully once; on file change, re-run `rust-analyzer scip` incrementally and have Claude re-summarize only changed modules (cheap, batched, offline). The local model never regenerates the index — it only consumes it.

**Retrieval: structural first, embeddings second.** For Rust, structural retrieval (SCIP symbol/reference lookup, call-graph traversal) is more reliable than embedding similarity because the relationships are exact. Use embeddings only as a fallback for fuzzy "where's the retry logic" queries. Aider's repo map is deliberately symbol-level, not semantic — for small projects that's a feature.

### Evals — cheap, Rust-specific
- **Custom smoke tests are your primary signal**, because they match your workload: "rename this function across the crate," "add a field to this struct and fix all constructors," "fix this failing test." Script each with a known-good outcome and a `cargo test` oracle. Fastest feedback loop; mirrors how SWE-bench's minimal harnesses (mini-swe-agent, single `bash` tool) isolate model from harness.
- **Aider polyglot (Rust subset)** for edit-format competence — it already includes Rust exercises with a two-attempt/test-feedback protocol.
- **Terminal-Bench**-style tasks if you add shell tools, but note the harness itself accounts for 10–25 points of score variance — measure *your* harness, per the "Agent = Model + Harness" framing.
- Track two numbers above all: **% well-formed tool calls** and **% edits that pass `cargo check` on first apply**. If either drops, the harness — not the model — is usually the culprit (context truncation, too many tools, wrong template).

## Recommendations

**Stage 0 — Prove the thesis before building the TUI (1–2 days).** Wire a throwaway script: Ollama + Qwen3-Coder-30B-A3B (Q4_K_M, `num_ctx` 32k), 3 tools (`read`, `apply_edit`, `run_check`), grammar-constrained tool block, hand-written `AGENTS.md` + a tree-sitter repo map for one small Rust crate. Run your 5 smoke tests. **Benchmark to change plans:** if first-apply `cargo check` pass rate is <60% *with* the index and grammar, the bottleneck is the model, not the harness — stay on Qwen3-Coder-30B (agentic-tuned, ~96% tool-call rate) rather than heretic, and consider dropping the tool count further.

**Stage 1 — Build the harness in Rust (fork the structure).** Lift the SQ/EQ loop and context-compaction design from `codex-rs`; use ratatui for the TUI. Implement: ReAct one-tool-per-turn, retry-with-repair (cap 3), search/replace editblock coder with unique-match verification, and the deterministic `cargo check` gate. Keep the tool surface at 3–5. Do **not** make native function-calling the primary path — grammar-constrain emission.

**Stage 2 — Build the index pipeline (spend most effort here).** `rust-analyzer scip` for structure, tree-sitter repo map for overview, Claude for `AGENTS.md` + per-module summaries. Store in `.agent-index/`. Wire retrieval so a task pulls: relevant summaries + symbol signatures + only the function bodies in the edit's blast radius. This is where you win or lose.

**Stage 3 — Tune and measure.** Two-phase reasoning-then-constrained-emission to recover the reasoning tax. Add embedding fallback retrieval only if structural retrieval misses. Track %well-formed-tool-calls and %first-apply-compile continuously; regressions almost always trace to context/tooling, not the weights.

**Model choice, direct:** For agentic reliability, **Qwen3-Coder-30B-A3B is the safer default than the heretic abliterated fine-tune**, because abliteration measurably erodes tool/structured-output reliability and heretic's retention of that specific capability is unproven. If you need heretic for content reasons, insulate it: grammar-constrain everything, keep tools ≤5, lean hard on the compile gate. Use `--jinja` with llama.cpp/llama-server for the correct tool-calling chat template; if using Ollama, verify the tool renderer matches the model's trained format (the Hermes-vs-Qwen3-Coder-XML mismatch is a known, active bug — issue #14493).

**Hardware, direct:** The Ryzen 9 5950X CPU-only box is fine for *interactive small edits* at ~8–15 tok/s but will feel sluggish on any multi-turn exploration — which is precisely why the index-first design is non-negotiable there. Set threads to ~16 physical cores (SMT hurts MoE). If the MacBook Pro (Apple Silicon Pro) is available, prefer it for development: MLX 4-bit at ~40–60 tok/s makes the ReAct loop tolerable, and MLX beats GGUF/Ollama on that hardware. Ensure total RAM comfortably exceeds the ~21GB model (24GB is marginal). Consider `ik_llama.cpp` on CPU if you hit the MoE-CPU slowdown.

## Caveats
- **Model-name/date drift in sources.** Several cited sources reference future-dated models (Qwen3.5/3.6, GPT-5.x, Claude Opus 4.6, M5). I've treated these as same-class MoE successors to Qwen3-30B-A3B where the architectural point holds; treat specific version numbers skeptically.
- **CPU tok/s figures are estimates, not a direct 5950X benchmark.** The ~8–15 tok/s range is triangulated from DDR5-CPU community reports (~12–15 tok/s) adjusted down for DDR4 bandwidth, plus bandwidth math. Your exact number depends on RAM speed, thread count, quant, and the llama.cpp MoE-CPU overhead issue (#19480, worst for Qwen3-Next). Benchmark on your box before committing.
- **Heretic-specific tool-calling data does not exist.** The degradation evidence is for abliterated Qwen generally (esp. huihui-ai variants); heretic's low-KL design *should* help but is unmeasured for function-calling/JSON. Genuine unknown — hence "insulate with grammar + compile gate."
- **Constrained-decoding reasoning tax is real but mitigable.** The 10–30% figure (Tam et al.) is from reasoning benchmarks under strict JSON mode; the two-phase reason-then-constrain pattern largely avoids it, and later work argues much of it is a prompt/schema artifact. Don't grammar-constrain the model's *thinking*, only its *action emission*.
- **Diff-XYZ nuance:** search/replace is clearly best for *strong* models, but small open models "benefit little from any formatting choice." Choose search/replace for *validation* reasons (easy to verify a unique on-disk match), not because it will rescue a weak model's accuracy — the compile gate does that.
- **Aider's 8% Qwen2.5-Coder-32B polyglot score** reflects that benchmark's difficulty and edit-format sensitivity, not that the model is useless for small edits — with editblock format, an index, and a compile gate, real-world small-edit success is much higher. Don't over-index on one leaderboard number.
- **Harness variance dominates.** The same model can swing 10–25 points across harnesses. Your smoke-test numbers are only meaningful for *your* harness; don't compare them to published leaderboards.
