# M0, the full five-task suite

2026-08-13. The first end-to-end run of the M0 smoke suite against a real
checkout, and the first time either M0 gate has had a number attached to it.

Three results, in descending order of usefulness.

**Neither model completed a single multi-site cascading task, in six attempts
each way.** `rename` and `add_field` went 0/3 for the driver and 0/3 for the
control. That is not a fact about a model. It is a fact about the harness, and
§6.2 changed twice today because of it.

**Seven defects in the harness were found by running it**, five of which made
the model look worse than it is and one of which was inflating the headline
metric with edits that changed nothing.

**The quality gate fails and the timing gate passes by a factor of fourteen.**

## The measurement was wrong before the harness was

Four of the five tasks had no oracle. The script fell back to "does the
workspace still compile", which is true of a workspace nobody has touched. The
control's first `rename` run would have scored a pass under that rule: it
searched, read, ran `check`, and called `finish` having made no edit at all.

Every task now has an oracle that checks the change is present, and `--selftest`
asserts each fails on a pristine tree. All five do. Each was also confirmed to
pass when the change is made correctly, which is the half that is easy to skip
and turned out to matter: the `add_field` oracle failed on a *correctly* added
field, because adding the field breaks two struct literals.

FACP also had a flattering denominator, counting only edits whose `search`
matched the file, so a fabricated edit never counted against the model. Both
denominators are now reported.

## What the numbers mean

**The failure is a cliff, not a slope.** Every failure in the suite is one of the
two tasks needing edits in more than one place. The three single-site tasks run
at 2/3 and 3/3. A harness that could handle cascading edits would take the driver
from 40% to something near 67% without touching the model.

**heretic's deficit on the tasks it can do is reliability, not capability.** It
completes each single-site task two times in three; the control completes each
three times in three and does so identically on all three trials. Perfect
consistency against 3, 1, 2 on identical inputs at the same temperature. So the
driver's problem is variance, which §6.3 attacks directly, rather than
competence, which it cannot.

**The control costs exactly twice the wall-clock**, 1,896s against 949s, for one
and a half times the completions. Consistent with the earlier six-turn A/B and
for the same reason: heretic decodes about 30% quicker and decode dominates.

**Twelve of heretic's fifteen tasks ended in a stall abort.** Stalling is the
failure mode, overwhelmingly, exactly as §8.3 characterised it. It does not
fabricate. It stops.

**The rollback mechanism is specified and effectively untested.** It fired twice
for the control and never for the driver across 90 turns. Recorded rather than
left to silence.

## Seven defects, found by running it

Each was making the model look worse than it is, and each costs zero model tokens
to fix. Full detail in RFC-0001 §6.2 and §6.3.

1. **The gate reverted failed edits**, making every change with no compiling
   intermediate state unreachable. The control proposed eight edits on
   `add_field`, all eight matching the file uniquely, none fabricated, all eight
   reverted. FACP recorded 0/8, which reads like a model that cannot write Rust,
   and the model had written a correct first edit. Edits now accumulate.
2. **The rollback triggered on elapsed redness**, three consecutive red gates,
   which is wrong for the same reason: `rename` is red three times running on its
   way to green. It fired one turn before success and threw away a correct
   rename. It now triggers on the rustc error count failing to fall.
3. **`finish` was taken on trust.** The control declared `rename` complete having
   made no edit, with every action well-formed and permitted.
4. **A green gate said nothing about what to do next**, so both models re-sent
   edits that had already landed. `fix_test` went from four turns to two.
5. **A repeated `read` was refused rather than paged.** heretic's first
   `add_field` run did nothing else at all.
6. **The stall check ran after the argument check**, so a repeated *malformed*
   action was never seen as repeating: twelve identical argument-less edits,
   twelve separate refusals, one per turn to the cap. It also compared only
   against the previous action, which A-B-A-B alternation defeats.
7. **Edits whose `replace` equalled their `search` were counted as passes.** The
   harness applied them, `cargo check` passed because nothing had changed, and
   FACP scored a first-apply pass. Two of five tasks in one trial "passed the
   gate" this way and failed their oracles. Every FACP figure taken before this
   fix, including the pilots below, is inflated by an unknown amount.

## Two things checked because they looked too tidy

`--all-targets` was adopted on the argument that plain `cargo check` cannot see
`#[cfg(test)]` code. The argument is right: a type error planted in
`dipper-index`'s test module gives plain `cargo check` exit code **0** and
`--all-targets` exit code **101**. The example first offered for it was wrong —
the `rename` failure was caught by plain `cargo check`, via a caller in
`dipper-cli` — and is recorded in RFC-0001 §6.2 as withdrawn.

Gate cost, three trials each, warm: **0.11s** unchanged, **0.31s** after a change
to the core crate that compiles and cascades to all four dependents, **0.20s**
for an edit that breaks its own caller, since compilation stops at the first
error. A first attempt at this figure measured a change that did not compile and
reported it as the cascading cost, which would have flattered the gate by 35% by
timing it not doing the work.

## Q2, the overlay, settled the same day

`scripts/overlay-probe.py`, four candidates against the same target.

| | build | aliases the working tree | gate, own target dir | gate, shared |
|---|---|---|---|---|
| `cp -R` | 0.03s | no | 13.2s cold, then 0.31s | 1.31s first, then 0.12s |
| `cp -Rc` (APFS clone) | 0.02s | no | 13.5s cold, then 0.31s | 0.50s first, then 0.12s |
| `cp -Rl` (hardlink) | 0.03s | **yes** | 13.3s cold, then 0.31s | 0.52s first, then 0.12s |
| `git worktree` | 0.03s | no | 13.1s cold, then 0.31s | 1.33s first, then 0.12s |

**The hardlink forest aliases.** The probe writes into the overlay the way a
naive tool writes, open-truncate-write, and then reads the working tree. The
working tree had changed. Not a trade-off; a disqualification.

**The shared target directory does not thrash**, which was the question that
mattered, because cargo fingerprints record absolute paths and an overlay at a
different path might have invalidated everything on every switch. It does not:
cargo keys units by package path and the two trees' artifacts coexist. The
no-op alternation above is not proof of that, since both trees were identical,
so it was measured again with the overlay diverged and a **fresh** edit each
round:

```
overlay(new edit) 0.29s   worktree(clean) 0.12s
overlay(new edit) 0.29s   worktree(clean) 0.12s
overlay(new edit) 0.29s   worktree(clean) 0.12s
```

Stable. Sharing the target directory saves the overlay a **13.2s** cold build at
session start and costs nothing per turn.

Answer: `cp -Rc` with a `cp -R` fallback, sharing the working tree's target
directory. A `git worktree` passes every test here and is rejected anyway,
because it materialises `HEAD` rather than the working tree: a session begun with
uncommitted changes would work against different code from the one on the user's
screen.

## A hypothesis that did not survive its own test

Mid-session the model began emitting `edit` actions with `search` and `replace`
empty. It happened on the two tasks whose prompts had been lengthened that
morning and on none of the three left alone, and a quick check gave 3 argument-
less runs in 5 for the longer `rename` wording against 0 in 4 for the shorter.
The obvious story was that a longer task statement degrades argument filling.

Tested properly on `add_field`, three runs each way (`HG_ADDFIELD=short`):

| | oracle | runs with an argument-less `edit` |
|---|---|---|
| long wording | 0/3 | 1/3 |
| short wording | 0/3 | **2/3** |

The effect is absent and the sample leans the other way. The earlier figures did
not reproduce. **Prompt length does not explain the argument-less edit**, the
cause is unknown, and the tidy explanation is withdrawn. Recorded because it is
the third time today that a plausible story survived right up until it was
measured, which is §12.1's entire point.

## The project brief: a large effect that vanished when controlled

M1's first question is whether the index earns its place, since the M0 tasks
pre-load the whole target file and the model may not consult the brief at all.

**Unpaired**, driver, three trials with `m0/dipper-brief.md` against a no-brief
run taken afterwards:

| | oracle |
|---|---|
| with brief (trials 1-2) | 4/10 |
| no brief (trials 1-2) | **0/10** |

With a mechanism that looked convincing: given no brief, the model paged through
the entire file across four turns (1-121, 122-242, 243-363, 364-413), exhausted
it, and stalled without ever proposing an edit. It read instead of acting.

That no-brief run then died on a socket read timeout, against a host that was
afterwards reachable but holding no model. Host drift is a live alternative
explanation for anything measured in it, so the two arms were run again **back to
back, sharing whatever state the machine was in**:

| | oracle |
|---|---|
| no brief | **2/5** |
| with brief, immediately after | **2/5** |

Level. The effect does not survive being controlled, and the no-brief arm in the
paired run proposed edits normally rather than reading to exhaustion. The
unpaired figures measured the ThinkPad, not the brief.

**Verdict: no measurable effect at this sample size**, which is five tasks an arm
and nowhere near enough to call it a null result either. It is unresolved, and it
should be resolved with paired trials before M1's semantic pass — the expensive
half, the half that spends the Opus subscription — is built on the assumption
that the model reads what it produces.

Kept in full because the discarded version was more interesting than the
surviving one, and because a 4/10-against-0/10 with a tidy mechanism attached is
exactly the sort of finding that gets written into a design document and believed.

## Open

The 12-turn cap now binds on `rename`: one trial reached the cap having gone from
three errors to one, with the work visibly still in progress. Whether the cap or
the model is the constraint on that task is untested, and it is the cheapest of
Q7's three candidate answers to try.

The argument-less `edit` itself. It appears across both models and both prompt
wordings, costs a turn each time, and has no known trigger.
